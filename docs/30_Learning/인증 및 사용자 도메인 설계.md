### 1. 핵심 문장의 쉬운 해석

> **"비즈니스 운영에서 동시에 일어나는 사건이라도, 데이터의 라이프사이클과 성격(스냅샷 vs 시간 이력)이 다르면 데이터 모델을 분리해야 하며, 아직 존재하지 않는 미래의 가상 시나리오 때문에 불필요한 상태 머신을 앞당겨 만들 필요는 없다."**

사용자께서는 "퇴사하면 계정도 안 쓰는데 왜 상태를 따로 둬야 하지? 테이블을 분리하면 상태도 똑같은 거 아닌가? 둘 다 켜짐/꺼짐 2가지 상태인데 왜 다르지?"라는 매우 자연스럽고 날카로운 직관적 의문을 던지며 개념의 본질을 파고들었습니다.

---

### 2. 등장한 개념의 일반적인 정의

* **관심사의 분리 (Separation of Concerns):** 시스템의 각 영역이 자신이 맡은 본질적인 책임(인증 vs 시설 점유)에만 집중하도록 구조를 나누는 원칙입니다.
* **단일 진실 공급원 (Single Source of Truth, SSOT):** 어떤 비즈니스 사실(예: 거주 중 여부)을 증명하는 데이터를 시스템 내 단 한 곳에만 두어 데이터 불일치(Data Anomaly)를 막는 원칙입니다.
* **스냅샷 상태(Snapshot State) vs 구간 이력(Temporal Interval):**
* **스냅샷:** '지금 이 순간'의 상태값 하나만 보관하며 변경 시 이전 값이 지워집니다 (`enabled = true/false`).
* **구간 이력:** 시작과 끝(`started_at`, `ended_at`)을 가지며, 과거의 기록들이 누적(Append)되어 시점별 조회가 가능한 데이터 모델입니다.


* **YAGNI (You Aren't Gonna Need It):** 실제로 요구사항이 발생하기 전까지는 미래를 예측하여 코드를 미리 복잡하게 만들지 말라는 소프트웨어 설계 원칙입니다.

---

### 3. 왜 이 개념 또는 원칙이 필요한지

* **데이터 유실 방지:** 퇴사했다고 해서 과거에 그 학생이 201호에 살았고, 냉장고 몇 번 칸을 썼는지에 대한 사실까지 사라져서는 안 됩니다. 단순 플래그로 덮어쓰면 과거 이력이 증발합니다.
* **상태 동기화 버그 원천 차단:** 거주 종료 플래그와 계정 비활성화 플래그를 두 군데에 따로 두면, 두 값이 서로 어긋나는 상황(예: 거주는 끝났는데 계정 플래그 갱신 실패로 로그인이 유지되는 현상)을 막기 위해 불필요한 트랜잭션과 테스트 코드가 늘어납니다.
* **쓰기 트랜잭션 비용 통제:** 비밀번호 잠금 등 복잡한 상태 전이를 미리 구현하면, 단순 읽기(인증 검사)여야 할 요청이 DB 락과 쓰기 트랜잭션으로 변질되어 성능 저하와 병목을 유발합니다.

---

### 4. 가장 단순한 예시

> **A. 단순 플래그 방식의 한계 (2가지 상태로 동일시한 경우)**
> ```text
> [User]
> id: 1, name: "김승현", is_active: false (퇴사해서 비활성화)
> 
> ```
> 
> 
> * 다음 학기에 재입사할 때 과거 거주 기록과 활동을 연결하기 어렵고, 언제 퇴사했는지 시점을 알 수 없습니다.
> 
> 

> **B. 이력 분리 모델 (시간 축을 둔 구조)**
> ```text
> [User (계정 식별)]
> id: 1, email: "sh@univ.ac.kr"
> 
> [Residence (거주 구간 이력)]
> id: 101, user_id: 1, room: "201호", started_at: 2025-03-01, ended_at: 2025-06-30
> id: 102, user_id: 1, room: "305호", started_at: 2025-09-01, ended_at: null (현재 거주 중)
> 
> ```
> 
> 
> * `ended_at IS NULL`인 행이 존재하는지 여부만으로 "현재 거주 중인가?"를 계산(파생)할 수 있으며, 과거 이력도 안전하게 유지됩니다.
> 
>

### 5. 반례와 적용하지 않아도 되는 경우

* **단기 행사/1회성 시스템:** 해커톤, 3일 캠프처럼 행사가 끝나면 참가자 계정과 모든 데이터를 DROP(폐기)하는 시스템이라면 이력 분리 없이 단순 Boolean 플래그 하나로 끝내는 것이 훨씬 경제적입니다.
* **초고빈도 대규모 분산 인증 환경:** 로그인 요청이 초당 수만 건이라 매번 이력 테이블 조인/계산 비용이 부담되는 환경이라면, DB 정규화를 일부 포기하더라도 `User` 테이블에 캐시성 플래그(`is_active`)를 비정규화하여 두는 것이 유리합니다.

### 6. 가능한 대안과 각각 적합한 조건

| 설계 대안 | 특징 | 적합한 조건 |
| --- | --- | --- |
| **대안 1. 단일 Boolean 플래그** | 테이블 1개에 `is_active` 하나만 두고 퇴사 시 비활성화 | 이력 추적과 재입사가 전혀 필요 없는 단순 토이 프로젝트 |
| **대안 2. 파생 상태 기반 로그인 판정** | `User`에 상태 컬럼을 두지 않고, 활성 `Residence` 유무로 로그인 허용 | 상태 동기화 버그를 없애고 최소 스키마로 가고 싶은 MVP 단계 |
| **대안 3. 최소 계정 플래그 + 거주 이력 테이블 (정석)** | `User.enabled`는 시스템 보안 차단용, `Residence`는 방 점유 이력용 | Spring Security 표준 구조를 따르며 향후 학생 제재/차단 확장성을 열어둘 때 |

### 7. DormMate 프로젝트에 적용하면 무엇이 달라지는지

* **일반 원칙:** 인증 주체(`User`)와 공간/자원 점유 자격(`Residence`, `FridgeSlotAssignment`)은 생명주기가 다릅니다.
* **프로젝트 문서에 명시된 사실:**
* DormMate Rebuild 백엔드의 `User` 엔티티는 현재 `email`, `role`, `nickname` 등으로 구성되어 있으며 별도의 `status`나 `isActive` 컬럼이 없습니다.


* 냉장고 칸 배정은 `FridgeSlotAssignment`를 통해 `assignedAt`과 `User`를 연결하여 별도 테이블로 분리 관리하고 있습니다.


* API 스펙에는 비활성 계정에 대해 `ACCOUNT_INACTIVE` 에러 코드를 반환하도록 정의되어 있습니다.




* **문맥에서 추론한 내용 (사용자의 고민 정리):**
* 사용자께서는 "어차피 거주 종료 시에만 비활성화할 건데 별도 상태를 두는 건 오버엔지니어링 아닌가?", "학생/관리자 테이블을 나누면 똑같은 것 아닌가?", "둘 다 켜짐/꺼짐 2가지 상태인데 왜 방식이 다르다고 하는가?"라는 현실적이고 실용적인 관점에서 고민하셨습니다.
* 이 고민을 통해 '관리자 화면에서의 단일 처리(UI)'와 '데이터베이스의 이력 보존(DB 모델링)'은 분리해서 생각해야 한다는 점, 그리고 '단순 플래그(스냅샷)'와 '날짜 구간을 가진 이력(시간 축)'은 겉보기엔 둘 다 2가지 상태처럼 보여도 데이터의 차원이 완전히 다르다는 점을 명확히 파악하셨습니다.


* **새로 제안하는 설계:**
* DormMate Rebuild에서는 아직 일어나지 않은 '비번 5회 실패 계정 잠금' 등을 위해 `UserStatus` Enum을 미리 파지 않습니다.
* Spring Security 연동 시 `User`에 `enabled` 컬럼을 억지로 추가하지 않고, **ADMIN 권한이거나 활성 거주 기록(`Residence.endedAt == null`)이 있을 때 통과**시키는 파생 검증을 활용할 수 있습니다.
* 만약 기존 API 명세의 `ACCOUNT_INACTIVE` 스펙을 준수해야 한다면, 거주 기록이 없는 학생이 로그인할 때 해당 에러 코드를 반환하도록 예외 매핑을 구성하면 스키마를 단순하게 유지하면서도 요구사항을 충족할 수 있습니다.

### 9. 사용자가 이해했는지 확인하는 질문

만약 기숙사 관리자가 "202호에 살던 학생을 203호로 방만 옮겨주는(호실 이동) 기능"을 실행해야 할 때, '계정 활성 플래그와 방 거주 상태를 한 테이블의 컬럼으로 합쳐둔 시스템'과 '거주 이력(`Residence`) 테이블을 따로 분리한 시스템'은 각각 내부 데이터가 어떻게 다르게 변경될까요?


**1. 계정 테이블 구조: 단일 User vs 분리(Student/Admin)**

* **질문:** 프론트엔드에서 학생/관리자 로그인 탭을 따로 두더라도 백엔드 테이블을 하나로 모으는 것과 쪼개는 것 중 무엇이 나은가?
* **핵심 결론:** **단일 `User` 테이블**이 유리함.
* 테이블을 쪼개면 스프링 시큐리티의 `SecurityFilterChain` 및 `UserDetailsService` 빈을 역할별로 2벌씩 만들어야 해 설정과 유지보수 비용이 2배로 뜀.
* 단일 테이블을 쓰면 체인 1개, 서비스 1개로 처리되며 권한(`Role`) 검사도 표준 방식으로 단순화됨.
* 브라우저 세션 쿠키(`JSESSIONID`)는 도메인당 하나만 유지되므로, 테이블 분리 여부와 무관하게 동일 브라우저 내 학생/관리자 동시 로그인은 어차피 불가능함.



**2. 테이블 분리 모델 vs 통합 모델의 특성 비교**

* **데이터 무결성:** 분리 모델(`User` + `StudentProfile`/`AdminProfile`)이 우세. 학생 전용 컬럼(학번 등)에 `NOT NULL` 제약조건을 깔끔하게 걸 수 있어 불필요한 NULL 데이터 방지.
* **조회 편의성/속도:** 단일 테이블(`User`)이 우세. 별도의 `JOIN` 없이 단일 테이블 조회로 쿼리가 단순함.

**3. 계정 활성화 상태와 거주 정보의 분리**

* **질문:** 거주 정보 유무로 로그인을 통제할 것인가, 아니면 계정 상태(`User.enabled`)와 거주 정보(`Residence`)를 분리할 것인가?
* **핵심 결론:** **인증(계정 활성)과 도메인 인가(거주 정보)를 분리**해야 함.
* '비밀번호 불일치', '계정 정지(비활성화)', '배정 호실 없음(미거주)'의 원인을 하나로 뭉뚱그리면 사용자 안내와 장애 디버깅이 어려워짐.
* 관리자는 애초에 `Residence`가 없으므로 인증 단계에 거주 정보 조회를 엮으면 예외 처리가 꼬임.



**4. 활성 거주지(호실 배정) 검증 시점 및 구현 방식**

* **질문:** 거주자 확인은 로그인 시점에 막을 것인가, 서비스 기능 호출 시점에 막을 것인가? 공통 로직은 어떻게 둘 것인가?
* **핵심 결론:** **서비스 레이어 검증 + 도메인 서비스 메서드 호출** 방식 채택.
* 외박 신청, 시설 예약 등 실제 방이 필요한 비즈니스 로직을 탈 때 `residenceService.getActiveResidence(userId)` 같은 공통 메서드로 조회하고 없으면 예외를 발생시킴.
* 복잡한 AOP나 URL 인터셉터 대신 순수 자바 메서드 위임 방식을 쓰는 것이 디버깅과 흐름 파악에 가장 안전함.



**1. 도메인 정의: '퇴소'와 '휴관'의 분리**

* **질문:** 퇴소를 '계정이 비활성화된 사건'으로 볼 것인가, '계정은 유지되나 거주 자격만 끝난 사건'으로 볼 것인가?
* **도메인 핵심 특성:**
* 이 기숙사는 퇴소 시 재입사가 불가능(영영 끝남)한 구조임.
* 반면 **휴관**은 퇴소가 아니라 "거주 계약은 유지되나 시설만 일시 이용 불가"인 상태임.


* **핵심 결론:**
* **퇴소 = 계정 비활성화 (`User.enabled = false`) + 거주 종료 (`Residence.endedAt`)**: 두 작업을 한 트랜잭션에서 함께 처리하며, 과거 이력(신청, 물품 등)은 보존함.
* **휴관 = 시설 운영 중단**: 계정이나 거주 정보는 건드리지 않고, 로그인 후 시설 예약 등 비즈니스 로직 단위에서만 일시 차단함.
* **방 이동 = 거주 정보 교체**: `User.enabled`는 유지하고 `Residence`만 교체함.



**2. 에러 코드의 의미 확정**

* **질문:** 퇴소자가 로그인할 때 나가는 `AUTH-015`의 의미는 무엇인가?
* **핵심 결론:** "배정 호실 없음" 같은 비즈니스 자격 에러가 아니라, "퇴소 또는 정지 등으로 인해 비활성화된 계정(ACCOUNT_INACTIVE)"이라는 인증 계층의 계정 비활성화 에러로 의미를 확정함.

**3. 인증 계약과 Spring Security 동작 순서의 충돌**

* **질문:** "비밀번호가 맞을 때만 비활성 사유(`AUTH-015`)를 알린다"는 계약을 Spring Security 기본 설정으로 만족할 수 있는가?
* **핵심 결론:** 기본 설정으로는 불가능함.
* Spring Security의 기본 동작(`DaoAuthenticationProvider`)은 비밀번호를 맞췄는지 확인하기 전(사전 검사)에 `isEnabled()`를 먼저 검사하여 바로 `DisabledException`을 던짐.
* 따라서 아무 비밀번호나 입력해도 비활성화 계정임이 노출되는 문제가 발생함.



**4. 인증 로직 커스텀 구현 방식**

* **질문:** 비밀번호를 먼저 검사한 뒤 비활성화 여부를 확인하려면 어떻게 구현해야 하는가?
* **핵심 결론:** **`DaoAuthenticationProvider` 상속 및 오버라이딩** 방식 채택.
* 사전 검사를 무력화하고, 비밀번호 매칭(`additionalAuthenticationChecks`)을 먼저 통과한 직후 `user.isEnabled()`를 직접 검사해 `DisabledException`을 발생시키는 방식으로 순서를 제어함.
