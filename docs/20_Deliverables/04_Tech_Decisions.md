# Tech Decisions

> 합의된 기술 결정과 근거를 기록한다. 구현 완료 여부는 `API_Implementation_Status.md`에서 별도로 관리한다.

## 1. 패키지 구조 (Global + Domain)
- **선택:** 루트는 `com.dormmate`로 통일한다. 최상위는 `global`과 `domain`으로 분리하며 현재 `domain`은 실제 구현 범위인 fridge와 user부터 구성한다. 규모가 큰 fridge는 slot/bundle/item 하위 모듈로 세분화한다. 인증·검사·관리자·알림 패키지는 해당 수직 슬라이스를 시작할 때 추가한다. 횡단 관심사(설정/보안/에러/공통 응답/유틸)는 `global`에 둔다.
- **근거:** Phase 1~5 범위와 API 그룹을 그대로 반영하면서 패키지 경로를 짧게 유지하고, 도메인 소유권/재사용 경계를 명확히 할 수 있다. 기능이 늘어나도 도메인 단위로 확장 가능하다.
- **대안:** 레이어 중심 구조만 유지(상위에 controller/service/repository)하거나, 하위 모듈 분리 없이 단일 도메인으로 유지.

## 2. 도메인 경계/중복 방지 기준
- **선택:** 큰 틀은 `global + domain`을 유지한다. `domain`은 기능 단위(Phase 기반)로 구성하되, 규모가 큰 도메인은 하위 모듈로 분리한다. 중복이 반복되는 것만 `global`로 승격한다.
- **실무 규칙:**
  - 반복 횟수만으로 `global`로 승격하지 않는다. 동일한 의미와 변경 이유를 공유하고 특정 도메인이 소유하기 어려울 때만 공통화한다.
  - “소유 도메인”을 정해 참조만 허용한다. User와 인증 자격증명의 경계는 인증 설계 시 별도로 확정한다.
  - 도메인 간 직접 의존은 최소화한다. 필요한 경우 공통 DTO/정책만 공유하고, 내부 로직은 분리한다.
  - 냉장고(fridge)처럼 큰 기능은 slot/bundle/item으로 분해해 책임을 축소한다.
- **근거:** 중복을 방치하면 규칙이 분산되고 복잡도가 상승한다. 명확한 승격 기준과 소유권 규칙이 유지보수 비용을 줄인다.
- **대안:** 초기부터 과도한 공통화를 진행하거나, 모든 로직을 단일 도메인에 유지하는 방식.

## 3. 오류 응답 표준 (ProblemDetail + code)
- **선택:** 모든 API의 오류 응답은 `application/problem+json`으로 통일하고, `ProblemDetail`에 `code`를 포함한다.
- **형식:**
  - `type`: URI (선택)
  - `title`: 요약 메시지
  - `status`: HTTP 상태 코드
  - `detail`: 상세 설명
  - `instance`: 요청 식별 URI (선택)
  - `code`: 오류 코드 (문자열)
  - `errors`: 필드 오류 맵 (선택)
    - 형식: `{ "field": ["message1", "message2"] }`
    - 예시: `{ "name": ["필수 입력입니다."], "expiryDate": ["날짜 형식이 올바르지 않습니다."] }`
- **코드 규칙:**
  - 공통 코드(HTTP 상태 기반):
    - `BAD_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `VALIDATION_FAILED`, `RATE_LIMITED`, `SERVER_ERROR`
  - 도메인 코드: 대문자 스네이크 케이스로 정의하고 OpenAPI/프론트 코드 매핑에 동기화한다.
- **근거:** 일관된 에러 계약을 통해 프론트/백엔드 간 메시지 매핑과 디버깅을 단순화한다.
- **대안:** HTTP 상태만으로 분기하거나, 모듈마다 임의의 에러 포맷을 사용하는 방식.
## 4. 폴더 구조 결정 (도메인 중심, Flat)
- **선택:** 도메인 중심 구조를 유지하되, 각 도메인 하위는 Flat으로 둔다.
- **근거:**
  - 모듈 확장성: 냉장고 외 확장 모듈 추가에 유리
  - 탐색 속도: 깊이를 줄여 파일 탐색 비용 감소

  - 학습 효율: 초보 개발자가 구조를 빠르게 파악 가능
- **대안:** 도메인 내부에 controller/service/repository/entity/dto 폴더를 중첩하는 레이어 구조

## 5. 점진적 ERD

- **상태:** Confirmed
- **날짜:** 2026-07-26
- **선택:** 전체 도메인 ERD를 먼저 확정하지 않고 현재 수직 슬라이스에 필요한 모델, 생명주기와 DB 제약만 설계한다.
- **근거:** 인증·검사·알림 정책이 미확정인 상태에서 전체 관계를 고정하면 재설계 비용이 커진다. 작은 범위의 계약·정책·테스트와 함께 모델을 확장하면 결정 근거를 추적할 수 있다.
- **적용:** `GET /fridge/slots`의 구체 범위는 호실 단위 Slot 배정 결정에 맞춰 다시 정의한다. 기존의 사용자 직접 `FridgeSlotAssignment` 전제는 사용하지 않는다.
- **대안:** 전체 ERD 선행 설계.

## 6. Slot 목록 입력 오류 처리

- **상태:** Confirmed
- **날짜:** 2026-07-26
- **관련 정책:** `INV-010`
- **선택:** 잘못된 `view`, 음수 `page`, 범위를 벗어난 `size`를 fallback 또는 clamp하지 않고 `400 ProblemDetail`로 반환한다.
- **근거:** 호출자 오류를 조용히 숨기지 않고 계약 위반을 조기에 발견하기 위해서다. `size=200`은 Slot 수가 제한적인 현재 UI 호환 범위로만 허용하며 다른 목록 API의 공통 기준으로 일반화하지 않는다.
- **대안:** 알 수 없는 값을 기본값으로 보정.

## 7. Redis는 Post-MVP 비교 후보

- **상태:** Confirmed
- **날짜:** 2026-07-26
- **선택:** Redis를 현재 아키텍처나 MVP 필수 의존성으로 두지 않는다. 검사 동시성은 DB 제약, 트랜잭션과 JPA 락을 먼저 검증한 뒤 Redis Lock과 비교한다.
- **근거:** 문제와 측정 없이 분산 락을 도입하지 않으면서 Redis 사용 경험과 기술 선택 근거를 함께 확보하기 위해서다.
- **조건:** Redis Session은 인증 방식과 배포 구조가 확정된 뒤 별도로 판단한다.

## 12. Slot MVP 모델과 확장 조건

- **상태:** Confirmed
- **날짜:** 2026-07-26
- **관련 정책:** `INV-012`, `INV-019`~`INV-023`
- **현재 선택:** Slot은 `slotId`로 식별하고 `fridgeId`로 물리적 냉장고에 소속시킨다. 사용자는 관리자가 지정한 필수 `displayName`으로 칸을 구분한다. 현재 표시 순서 요구가 없으므로 `slotIndex`, `slotLetter`, `position`, `displayOrder`는 도입하지 않는다.
- **기존 의도:** 기존의 `floorNo + slotIndex` 구조는 층 안에서 Slot을 바로 구분하고 Fridge 조회나 조인을 줄이려는 의도로 도입됐던 것으로 검토했다. `slotLetter`는 `slotIndex`를 `A`, `B`, `C`로 바꾼 사용자 표시값이었다.
- **대안 검토:** Slot에 `floorNo`와 층 단위 위치값을 직접 저장하고 물리적 Fridge 관계를 생략하는 방식을 검토했다.
- **대안을 선택하지 않은 이유:** Fridge는 관리자 추가·삭제와 물리적 설비 관리에 필요한 개념이다. 현재 규모에서 FK/PK 기반 Fridge 조인이 병목이라는 근거가 없으며, 측정 없이 조회를 줄이기 위해 관계를 제거하면 Slot의 층 정보와 냉장고 소속을 별도로 동기화해야 한다.
- **MVP 근거:** 영속 식별, 냉장고 소속과 사용자 구분이라는 현재 요구는 `slotId`, `fridgeId`, `displayName`으로 충족된다. UUID인 `slotId`는 API 관계와 영속 식별에는 적합하지만 사용자가 기억하거나 실물 냉장고와 대조하기에는 부적합하므로 사용자 표시는 `displayName`이 담당한다. 순서나 알파벳 계산 필드를 미리 추가하면 역할이 겹치고 변경 규칙만 늘어난다.
- **조회 선택:** 거주자는 현재 거주 호실에 활성 배정된 Slot을 조회한다. `RETIRED` Slot의 포함 여부와 변경 제한은 호실 단위 배정에 맞춰 Slot Task에서 다시 확정한다.
- **현재 정렬:** `floorNo → fridgeId → displayName → slotId`를 사용한다. `fridgeId` 순서는 업무상 표시 순서가 아니라 냉장고별 그룹과 페이지 결과를 안정적으로 유지하기 위한 기술적 순서다.
- **현재 단순화:** Fridge는 Slot 조회에 필요한 식별자와 설치 층부터 설계한다. 냉장고 표시명·운영 상태·삭제 생명주기와 Slot 표시 순서 관리는 해당 관리자 기능에서 확장한다.
- **재검토 조건:** 실제 쿼리와 실행 계획에서 Fridge 조인이 병목으로 확인되면 인덱스를 먼저 검토하고, 부족할 때만 `floorNo` 비정규화를 비교한다.
- **재검토 조건:** 관리자가 냉장고나 칸의 표시 순서를 직접 관리해야 하거나, 물리적 위치 기반 정렬이 사용자 흐름에 필요하다고 확인되면 `displayOrder` 또는 별도 위치 모델을 비교한다.
- **재검토 조건:** Slot 퇴역 후 이름 재사용, 복구, 감사 이력 요구가 확정되면 `displayName` 유일성 범위와 당시 표시명 스냅샷을 다시 설계한다.

## 13. 포장 영속 식별자와 사용자 라벨 분리

- **상태:** Partial Confirmed
- **날짜:** 2026-07-26
- **관련 정책:** `INV-013`, `INV-014`, `INV-016`~`INV-018`
- **현재 선택:** 포장의 영속 식별에는 UUID `bundleId`를 사용한다. 사용자용 `labelNumber`는 동일 Slot 안의 `1..999` 정수로 저장하고 화면에서 3자리로 표시한다. 관계와 유일성 검토의 원천은 `slotId`와 `labelNumber`이며, `"001"`이나 조합 문자열을 영속 식별자로 사용하지 않는다.
- **근거:** 앞자리 0은 데이터 의미가 아니라 표시 형식이다. 숫자로 저장하면 범위 검증과 비교가 단순하고 `"1"`과 `"001"`이 서로 다른 값으로 저장되는 문제를 피할 수 있다. 표시 형식 변경도 저장 구조에 영향을 주지 않는다.
- **용어 선택:** `포장 번호`는 `bundleId`와 `labelNumber`를 혼동시키므로 공식 용어로 사용하지 않는다.
- **아직 확정하지 않음:** 번호 발급 알고리즘, 동시 생성 제약, `999` 소진 처리, 소프트 삭제 후 재사용, 복원 충돌, `slotLabel`·`labelDisplay`의 최종 계약은 Bundle 생성 수직 슬라이스에서 확정한다.

## 14. 인증 전달 방식과 도메인 권한 입력 분리

- **상태:** Confirmed
- **날짜:** 2026-07-26
- **관련 정책:** `AUTH-001`, `AUTH-004`, `AUTH-006`~`AUTH-009`
- **인증 선택:** Spring Security 서버 세션과 `HttpOnly`, `SameSite=Lax` 쿠키를 사용한다. 배포 HTTPS 환경에서는 `Secure`를 적용한다. MVP는 단일 백엔드 인스턴스의 메모리 세션만 사용하며 Bearer Access Token, Refresh Token, `deviceId`, Redis Session은 도입하지 않는다. 토큰 인증은 `AUTH-011`의 Post-MVP 후보로 분리하고 필요성과 세션 병행 여부부터 다시 결정한다.
- **CSRF:** Spring Security의 CSRF 보호를 유지하고 SPA가 토큰을 변경 요청 헤더로 전달한다. 로그인과 `POST` 로그아웃도 CSRF 검증 대상이다.
- **로그인 응답:** `POST /auth/login` 한 번으로 세션 생성과 사용자 프로필 조회를 완료한다. 성공 시 `200 OK`와 `UserProfileResponse`를 반환하고 세션 식별자는 `HttpOnly` 쿠키에만 둔다. 별도 로그인 응답 래퍼와 토큰 쌍은 MVP 응답에 사용하지 않는다.
- **로그인 전 CSRF 준비:** 로그인 화면 진입 시 `GET /csrf`를 호출하고 응답의 헤더 이름과 토큰을 메모리에만 보관한다. 준비가 끝난 뒤 로그인 제출을 허용하여 버튼 클릭 시에는 `POST /auth/login` 한 번만 발생하게 한다.
- **자격 증명 실패:** 존재하지 않는 아이디와 잘못된 비밀번호를 외부에서 구분하지 않고 `401 AUTH_INVALID_CREDENTIALS`로 통일한다. 상세 원인은 내부 보안 로그에만 남겨 계정 존재 여부가 노출되지 않게 한다.
- **비활성 계정:** 올바른 자격 증명으로 비활성 계정에 로그인하면 `403 ACCOUNT_INACTIVE`를 반환한다. 사용자가 관리자에게 문의할 수 있도록 상태는 알리되 비활성 사유와 내부 메모는 노출하지 않는다.
- **CSRF 실패:** 토큰 누락·불일치·만료는 외부에서 세분화하지 않고 `403 CSRF_INVALID`로 통일한다. 프론트는 해당 오류를 일반 권한 부족과 구분해 기존 토큰을 폐기하고 새 토큰이 준비될 때까지 재제출을 막는다.
- **로그아웃:** 요청 본문 없는 `POST /auth/logout`으로 현재 세션과 쿠키를 정리하고 `204 No Content`를 반환한다. 세션이 이미 없어도 같은 결과를 반환하며 CSRF 실패만 `403 CSRF_INVALID`로 구분한다.
- **도메인 경계:** Controller 경계에서 Spring Security의 인증 주체를 `CurrentActor(userId, accountAuthorities)`로 변환한다. Service는 `Authentication`, `HttpSession`, 쿠키나 토큰 객체를 받지 않는다.
- **변동 권한:** 거주 자격, 냉장고 담당자 여부와 관리 Slot은 세션이나 `CurrentActor`에 캐시하지 않고 DB의 현재 활성 배정을 조회한다. 냉장고 담당자는 거주자 권한을 유지하며 관리 범위는 `SlotManagerAssignment`로 표현한다. 관리자처럼 계정 자체에 부여되는 권한만 `accountAuthorities`에 둔다.
- **근거:** HTTP 인증 기술을 업무 권한 로직과 분리하고, 배정 변경 후 이전 권한이 세션 만료까지 남는 문제를 방지하기 위해서다.
- **오류 경계:** 인증 주체를 복원하지 못하면 `401`, 인증됐지만 지원 역할·업무 자격이 없으면 `403`, 허용 범위에 데이터가 없으면 `200` 빈 목록을 반환한다.
- **재검토 조건:** 다중 인스턴스 배포나 세션 공유 요구가 생기면 Spring Session과 Redis를 비교한다. 모바일·외부 클라이언트 등 쿠키 세션만으로 해결하기 어려운 소비자가 생기면 Post-MVP 토큰 인증을 검토한다.
- **아직 확정하지 않음:** idle timeout의 구체값, 동시 로그인 제한, 다중 기기와 강제 로그아웃 정책.

## 16. 층별장 역할을 냉장고 담당 업무로 재설계

- **상태:** Confirmed
- **날짜:** 2026-07-26
- **관련 정책:** `INV-009`, `AUTH-004`, `AUTH-006`, `AUTH-009`, `INSP-001`
- **기존 설계 의도:** 층별장은 해당 층 거주자 중에서 선발하므로 `FLOOR_MANAGER` 역할과 사용자의 거주 층을 조합해 해당 층 냉장고 전체의 조회·검사 권한을 계산하려 했다. 당시에는 층별장이 자기 층 전체를 담당한다는 단순한 운영 흐름을 빠르게 표현하기 위한 설계였다.
- **확인된 문제:** 거주 위치와 관리 업무의 생명주기가 결합되고, 방 이동 시 관리 권한이 암묵적으로 이동할 수 있다. 일부 Slot 분담, 복수 담당자와 다른 층 지원을 표현하기 어렵고 담당 시작·해제 이력도 별도로 남길 수 없다.
- **용어 변경:** 원본 UI·문서의 “층별장”은 당시 요구사항을 설명하는 Legacy 용어로 보존한다. Rebuild의 사용자 용어는 “냉장고 담당자”, Java 모델은 `SlotManagerAssignment`, DB 테이블은 `slot_manager_assignments`를 사용한다.
- **최종 선택:** 냉장고 담당자는 활성 거주자에게 추가하는 기간성 업무로 보고, 관리 권한은 `SlotManagerAssignment(userId, slotId, assignedAt, releasedAt, assignedBy)`를 통해 Slot 단위로 저장한다. 냉장고 담당자는 거주자 권한을 유지한다.
- **UI 경계:** 층 전체 선택은 별도 층 권한이 아니라 현재 활성 Slot에 관리 배정을 일괄 생성하는 UI·Application Service 편의 기능이다. 개별 Slot 선택도 같은 저장 모델을 사용한다.
- **새 Slot:** 층 전체 일괄 배정 이후 추가된 Slot은 기존 담당자에게 자동 배정하지 않는다. 관리자가 새 Slot의 담당 범위를 명시적으로 확인한다.
- **조회 범위:** 거주자의 기본 이용 범위는 현재 거주 호실에 활성 배정된 Slot이다. 이 결과와 냉장고 담당자의 관리 Slot을 같은 API에서 합칠지, 관리자는 같은 API로 전체를 조회할지는 Slot Task 범위 재정의에서 다시 확정한다.
- **대안을 선택하지 않은 이유:** 층 전체와 선택 Slot을 별도 권한 타입으로 저장하면 현재 냉장고 관리 한 가지 업무를 위해 우선순위와 자동 포함 규칙이 추가된다. 현재 요구는 Slot 단위 배정과 UI 일괄 처리만으로 충족된다.
- **재검토 조건:** 새 Slot을 기존 층 담당자에게 반드시 자동 포함해야 하는 운영 요구가 확인될 때만 층 범위 권한이나 범위 타입을 비교한다.

## 17. 관리자 권한과 거주자 소유권 분리

- **상태:** Confirmed
- **날짜:** 2026-07-26
- **관련 정책:** `AUTH-010`, `ADM-001`, `ADM-003`
- **기존 검토:** 관리 편의를 위해 관리자에게 물품 등록 등 거주자 API 권한을 함께 부여하는 방안을 검토했다.
- **선택하지 않은 이유:** 관리자는 거주하지 않으므로 거주 Slot, 포장 소유자, 허용량, 비공개 메모와 벌점 귀속을 정할 수 없다. 관리자에게 거주자 권한을 상속하면 데이터 소유자와 운영 행위자가 혼동된다.
- **최종 선택:** 관리자는 계정의 `ADMIN` 권한으로 전체 조회와 별도 운영상 정정·강제 삭제를 수행한다. 일반 거주자 API로 관리자 소유 포장을 생성하지 않는다.
- **운영 기록:** 관리자 변경 행위는 대상 데이터와 수행자, 수행 시각과 사유를 기록한다. 구체 감사 로그 모델은 관리자 수직 슬라이스에서 확정한다.
- **확장 조건:** 관리자의 물품 등록 요구가 확인되면 관리자를 소유자로 만들지 않고 대상 거주자와 사유를 명시하는 대리 등록 API를 별도로 설계한다.

## 18. 냉장고 Slot의 호실 단위 이용 배정

- **상태:** Confirmed
- **날짜:** 2026-07-26
- **관련 정책:** `INV-001`, `INV-009`, `INV-023`, `INV-025`~`INV-027`
- **운영 사실:** 냉장고 칸은 같은 층의 호실들을 순서대로 구간화해 공통 배정한다. 현재 기본값인 냉장 3칸·냉동 1칸은 물리적 냉장고 한 대의 고정 구성이 아니라 호실 배분 계산에 사용하는 정책이다. 24개 호실이면 냉장 Slot 하나당 8개 호실, 냉동 Slot 하나는 24개 호실이 공동 사용한다.
- **기존 후보:** `FridgeSlotAssignment(userId, slotId, assignedAt, releasedAt)`로 사용자마다 이용 Slot을 직접 저장하려 했다. 관리 UI에서 성별·층·호실로 사용자를 선택한 뒤 사용자 배정을 일괄 생성하는 방식도 검토했다.
- **확인된 문제:** 실제 정책의 주체는 사용자 개인이 아니라 호실이다. 사용자 직접 배정은 같은 호실 구성원 수만큼 관계가 중복되고, 신규 입주·퇴사·방 이동 때마다 배정을 별도로 동기화해야 한다. 일부 사용자만 누락되면 같은 호실 구성원의 이용 범위가 달라지고, 저장된 결과만으로 호실 배분 정책을 설명하기 어렵다.
- **대안:** 사용자 직접 배정을 유지하는 방식, 호실·층·성별로 요청마다 Slot을 계산하는 방식, 호실 배정에 사용자별 예외 배정을 추가하는 방식을 비교했다.
- **선택:** `RoomSlotAssignment(roomId, slotId, assignedAt, releasedAt)`로 호실과 Slot의 기간성 배정을 저장한다. 사용자는 현재 활성 `Residence`를 통해 Room을 찾고, 그 Room의 활성 Slot 배정을 이용한다. 실제 예외 요구가 확인되기 전까지 사용자별 Slot 배정은 도입하지 않는다.
- **UI 경계:** 성별·층·호실 선택은 배정 대상을 찾고 여러 `RoomSlotAssignment`를 생성하는 관리자 편의 기능이다. 성별 자체나 선택 시점의 사용자 목록을 냉장고 이용 권한으로 저장하지 않는다.
- **방 이동:** 사용자의 현재 Residence가 바뀌면 이용 가능한 Slot도 새 호실 기준으로 바뀐다. 이전 호실을 통해서만 접근 가능한 Slot에 사용자 소유 포장이 남아 있으면 먼저 정리한 뒤 방 이동을 완료한다. 구체 확인 쿼리와 실패 응답은 거주 이동 또는 Bundle 수직 슬라이스에서 계약한다.
- **재검토 조건:** 같은 호실 구성원에게 서로 다른 Slot을 배정해야 하는 실제 운영 요구가 생기거나, 방 이동 후에도 특정 사용자가 이전 Slot을 계속 이용해야 한다면 사용자별 예외 배정을 별도 정책으로 검토한다.
