# 인증 및 사용자 도메인 설계

## 범위와 완료 조건

첫 로그인과 `GET /profile/me`, 일반 거주자의 `GET /fridge/slots`에 필요한
계정·권한·호실·거주 관계의 최소 도메인 모델을 결정한다. 구현 전에 개념의 책임,
생명주기, 저장 상태와 파생 상태, 관계와 무결성 조건을 코드 없이 먼저 검토한다.

이번 Task에서 다룬다.

- MVP 계정 공급과 개발환경 전용 seed 경계
- 계정, 관리자 권한, 거주 자격, 호실과 냉장고 담당 업무의 구분
- 계정 활성 상태와 Residence 유효기간의 의미와 저장 여부
- 첫 수직 슬라이스 검증에 필요한 최소 계정 유형
- 관련 정책·ERD·인증 계약의 일치 여부

이번 Task에서 구현하지 않는다.

- Entity, Repository와 전체 인증 코드
- 온라인 회원가입·승인과 관리자 계정 발급 API
- 운영환경의 최초 관리자·사용자 공급 절차
- Post-MVP 계정 잠금·정지 기능을 요구사항 없이 선행 구현

완료하려면 사용자가 최소 모델과 상태 의미를 설명할 수 있고, 확정된 정책은
Policy Baseline에, 중요한 기술 결정은 Tech Decisions에 반영되어야 한다.

## 현재 확정 사항

- `AUTH-002`: MVP는 온라인 회원가입과 관리자 계정 발급 API를 제공하지 않는다.
  계정·호실·거주 관계는 개발환경 전용 seed로 준비한다.
- 관리자는 거주자가 아니며 계정의 `ADMIN` 권한으로 동작한다(`AUTH-010`).
- 냉장고 담당자는 별도 영구 계정 역할이 아니라 활성 거주자에게 추가되는
  `SlotManagerAssignment` 기간성 업무다(`AUTH-004`, `AUTH-006`).
- 프론트 fixture는 백엔드를 우회하므로 실제 인증·권한 통합 검증 근거가 아니다.

## 설계 고민 — 계정 활성 상태와 거주 상태

### 판단 과정

처음에는 학생과 관리자를 별도 테이블로 둔다면 퇴사가 곧 계정 비활성화이므로,
학생의 거주 상태와 로그인 가능한 상태를 하나의 `is_active`로 관리할 수 있다고
생각했다. 그러나 계정 잠금, 거주 종료와 방 이동은 서로 다른 사건이어서 하나의
상태로 합치면 의미가 왜곡될 수 있다고 판단했다.

Residence의 유효기간에서 현재 거주 여부를 파생하면 이력도 보존하고 중복 플래그의
불일치를 줄일 수 있다는 점을 이해했다. 한편 MVP에는 퇴사 외의 계정 정지 요구가
없어 별도 계정 상태가 과한지, 2~300명 규모에서 활성 Residence 조회 비용이 문제가
될지도 고민했다. 현재는 예상 트래픽만으로 중복 상태를 저장하지 않고 실제 쿼리로
판단하기로 했다. 학생과 관리자를 별도 테이블로 둔다는 전제도 아직 확정하지 않았다.

### 현재 결정

- 계정 활성 상태와 거주 상태는 의미상 다른 개념으로 구분한다.
- Residence 유효기간에서 현재 거주 여부를 파생하는 방안을 우선 후보로 둔다.
- 계정 활성 필드 저장과 공통 계정 모델은 당시 미결이었으나 아래 합의와
  `영구 퇴소와 로그인 실패` 결정으로 해소했다.

### 검증 계획

- 활성 Residence 중복 방지 제약과 조회 인덱스를 모델 설계에서 검토한다.
- 로그인·프로필 수직 슬라이스에서 사용자 한 명의 활성 Residence 조회 쿼리와
  실행 계획을 확인한다.
- `AUTH-014`, `AUTH-015`의 로그인 실패 결과를 각각 테스트한다.
- Residence가 없는 일반 계정의 로그인·프로필 응답을 계약 전에 결정한다.

## 설계 합의 — 공통 User 인증 주체

### 판단 과정

처음에는 학생과 관리자를 별도 테이블로 나누는 방안을 생각했다. 하지만 둘 다 같은
로그인과 세션 인증을 사용하므로 테이블을 나누면 인증할 때 두 저장소 중 어디에서
사용자를 찾을지 처리해야 하고, 로그인 아이디 중복과 비밀번호 관리도 두 경로에서
일관되게 유지해야 한다. 공통 User 한 곳에서 인증 정보를 확인하는 편이 구현과
유지보수가 단순하다고 판단했다.

User에 학생·관리자 전용 컬럼을 모두 넣어 불필요한 NULL을 만들기보다, 생명주기가
다른 거주 정보와 권한·냉장고 담당 업무를 각각의 관계로 분리하기로 했다.

### 현재 결정

- 로그인과 세션 인증의 주체는 공통 `User`로 관리한다.
- 거주 정보는 `Residence`, 관리자 여부는 계정 권한으로 관리한다.
- 냉장고 담당 업무는 `SlotManagerAssignment`로 관리한다.
- 전용 필드가 확인되지 않은 `StudentProfile`, `AdminProfile`은 만들지 않는다.
- API의 프로필 응답은 필요 데이터를 조합한 DTO이며 같은 이름의 Entity를 요구하지 않는다.

## 다음 논의

공통 User와 계정 비활성 정책을 바탕으로 첫 개발 seed의 최소 계정·거주 사례를
정의한다. 활성 Residence 판정과 중복 방지 제약은 데이터 모델 설계에서 검토한다.

## 추가로 확인한 운영 사실 — 퇴소와 휴관

- 사용자가 경험한 기숙사에서는 일반 퇴소 후 다시 입소하지 않는다.
- 휴관은 퇴소가 아니며 거주계약과 거주 이력을 유지한다.
- 휴관 중에는 거주자 로그인을 차단한다. 관리자는 시설 추가·수리 등 운영 작업을
  위해 로그인할 수 있어야 한다.
- 원본 Feature Inventory에는 탈퇴 후 계정 비활성화와 이력 조회가 제시되어 있지만,
  휴관 정책은 명시되어 있지 않다. UI Flow에는 관리자 로그인 후 냉장고 운영·계정
  관리 흐름이 있으나 휴관 시작·종료 화면과 흐름은 없다.

### 범위 결정

휴관은 기숙사 운영에 필요한 기능이지만 Release 1에서는 구현하지 않고 후속
확장으로 둔다. 휴관 중 거주자 로그인을 차단하고 관리자 로그인은 허용하되,
거주계약과 거주 이력은 유지한다. 휴관을 User 비활성이나 Residence 종료로
표현하지 않는다. 시작·종료 방법과 로그인 실패 계약은 후속 Task에서 확정한다.
이 결정만으로 기존 `AUTH-003`, `AUTH-015`의 의미를 변경하지 않는다.

## 설계 합의 — 영구 퇴소와 로그인 실패

### 판단 과정

이 기숙사에서 영구 퇴소자는 재입소하지 않으므로 거주 관계를 종료하고 계정도
비활성화하는 것이 맞다고 판단했다. 비밀번호가 실제로 맞는데도 불일치라고
응답하면 본인과 행정실이 퇴소로 인한 로그인 차단 원인을 파악하기 어렵다.
반대로 비밀번호가 틀린 요청에 계정 비활성을 알리면 계정 상태가 노출된다.

### 현재 결정

- 영구 퇴소에서는 활성 `Residence`를 종료하고 `User.enabled = false`를 같은
  트랜잭션에서 적용하며 계정·거주·물품 이력은 보존한다.
- 올바른 자격 증명의 비활성 계정만 `403 ACCOUNT_INACTIVE`로 응답한다.
  틀린 비밀번호는 `401 AUTH_INVALID_CREDENTIALS`로 응답한다. 어느 실패에서도
  세션을 만들지 않는다.
- 휴관은 영구 퇴소가 아니므로 `User.enabled`와 `Residence`를 변경하지 않는다.
- 영구 퇴소 처리 API·관리자 UI는 이 Task에서 구현하지 않는다.

### 검증 계획

- 활성·비활성 계정 각각에 대해 올바른 비밀번호와 틀린 비밀번호의 응답을 검증한다.
- 퇴소 처리 수직 슬라이스에서 두 상태의 원자적 변경과 이력 보존을 검증한다.
- Spring Security의 계정 상태 선검사가 외부 오류 계약을 깨지 않는지 확인한다.
