# 문서 역할 및 기록 방식 정비

## 범위와 완료 조건

기존 문서의 좋은 기록 방식을 보존하면서 주제별 문서 생성, 합의 시점 기록,
과거 판단과 현재 기준의 구분을 정리한다. 문서 내용 확인·상호 참조·차이 검증을
완료 조건으로 삼으며 업무 코드 구현·실행 검증 완료를 뜻하지 않는다.

검토 대상은 작업 시작 시 저장소의 Markdown 문서 25개다.

- 루트 3개: README, AGENTS, Antigravity 지침
- Blueprint 2개: Feature Inventory, UI Flow
- Workspace 최상위 8개: Phase 0~5, API 구현 현황, 프론트 연동 기준
- Task 2개: Slot 조회, 개발환경 구축
- Troubleshooting 4개: 사용자 필드, 테스트 DB, 최소 물품 수, 폴더 구조
- Deliverables 6개: Architecture, ERD, OpenAPI, Tech Decisions, Issue Highlights, Policy Baseline

OpenAPI는 모든 경로·스키마·공통 응답을 확인했지만 각 API의 정책 합의나 실제
코드 동작 검증을 완료한 것은 아니다. Blueprint 원본, OpenAPI와 코드 변경은 제외한다.

## 합의 기록

### Task와 Troubleshooting을 주제별로 관리

- **배경:** “기존 문서를 사용한다”는 지침이 새 주제의 문서 생성을 금지하는 뜻으로
  읽혔고, Task 완료 후 기록만 강조해 실제 합의 기록 방식을 충분히 반영하지 못했다.
- **결정:** Task는 작업별, Troubleshooting은 문제 주제별로 생성한다. 같은 주제는
  갱신하고 Task의 결정·이유·제외 형식에 배경·검증·재검토 조건을 필요한 만큼 보완한다.
- **이유:** [Slot Task](./Task_Slot%20조회%20및%20검증.md)의 합의 흐름과
  [Tech Decisions](../../20_Deliverables/04_Tech_Decisions.md)의 기존 의도·대안·재검토
  조건을 보존해야 면접에서 선택의 맥락과 결과를 연결할 수 있다.
- **제외:** 모든 항목을 의무화하거나 모든 설계 합의를 별도 보고서로 분리하지 않는다.
- **기준:** [AGENTS.md 기록 규칙](../../../AGENTS.md#8단계--기록-정리와-회고).

### Phase와 Task의 목적 구분

- **문제:** Task의 기록·면접 복습 기능을 강조하면서 작업을 진행하는 본래 목적이 흐려졌다.
- **결정:** Phase는 단계 목표·범위·Task 구성·전체 현황을, Task는 개별 작업의 범위·합의·구현·검증을 관리한다.
- **이유:** 단계의 완료 판단과 개별 작업의 상세 실행을 구분하고, 합의 기록은 실행 문서 안에서 이어가야 한다.
- **제외:** Phase에 Task의 상세 내용을 복사하거나 면접용 회고만을 목적으로 Task를 만들지 않는다.

### Troubleshooting의 면접 대비 목적 명확화

- **문제:** 독립적인 설계 고민을 보관하는 문서로 넓혀 설명해 사용자의 의도와 달라졌다.
- **결정:** 실제 문제·생각과 판단·해결 행동·확인 결과를 주제별로 정리한다. 단순 설계 고민은 Task에 둔다.
- **이유:** 사용자가 면접에서 자신의 문제 해결 과정을 근거와 함께 설명하려는 목적이다.
- **제외:** 기존 설계 메모를 실제 해결 경험으로 재작성하지 않는다. 원문과 링크를 보존하고 면접 활용 상태를 표시한다. 미해결 기록은 해결 사례와 구분한다.

### 과거 기록을 보존하면서 적용 상태 표시

- **결정:** 원문을 지우거나 당시 결론을 새 결론으로 바꾸지 않고, 현재 적용 여부와
  대체한 정책·결정 링크를 앞에 둔다. 실제 검증은 수행 시점과 조건을 구분한다.
- **이유:** 다음 기록은 현재 구현 지시로 읽으면 정책·범위와 충돌한다.

| 발견 | 처리 |
| --- | --- |
| 빈 포장 허용 검토가 `INV-006`과 반대 | 설계 아이디어 원문 보존, 현재 미적용과 확정 정책 연결 |
| 사용자 필드 기록의 벌점·관리자 필수 구현 | 당시 판단 보존, 후속 범위·점진적 ERD 연결 |
| 개발환경 Task의 Doing과 계층별 전체 구현 순서 | 과거 학습 참고로 표시, 현재 Phase·Slot Task 연결 |
| 테스트 DB 해결 문서의 “현재 구성”이 해결 전 상태 | 당시 구성·검증 결과로 구분, 최근 Phase 0 재현 기록 연결 |
| Tech Decisions에 제거된 `view` 검증이 현재 선택으로 잔존 | 당시 선택 보존, `INV-030`과 현재 적용 연결 |
| ERD의 관리 배정 모델이 첫 Slot Task의 필수처럼 보임 | 후속 관계임을 명시하고 초안 보존 |
